## 四、高频问答（按提问概率排序）

### Q1 ★★★ 你这个项目里 RAG 用在哪？

**骨架**：Schema 召回 → 本质是 RAG，只是把"文档"换成"表结构"。

> 四环节一一对应：**切块**是一张表一个 chunk，**索引**是表名+注释+字段名，**召回**是打分取 topK，**增强**是把命中的表拼进 prompt。
>
> 有个点特别想讲：**字段的真实取值是最强的召回信号**。用户说的"支出"，其实是 `status` 字段的**取值**，而表注释里根本没有"支出"这个词。把取值纳入索引，召回率才上得来。
>
> 还有**两阶段召回**：只按词面打分有盲区——问"餐饮花了多少钱"，会召回分类表，但金额在交易表里，模型拿到维表写不出 SQL。所以我加了一跳**基于主键名的双向关联扩展**，把 JOIN 需要的表补上。不用外键约束是因为真实项目里外键几乎都不建。
>
> 代价我量化过：扩展把压缩率从 92.6% 拉到 87.4%，这是召回率和精确率的权衡。

### Q2 ★★★ 你怎么保证模型生成的 SQL 是安全的？

**骨架**：三道防线 + 为什么不用黑名单 + 真正的兜底是账号。

> **三道防线**：① 代码层 SqlGuard 做 8 步校验（去注释、多语句检测、语法解析、只允许 SELECT、表白名单、危险函数扫描、强制行数上限）；② 执行超时；③ 数据库账号本身只给 SELECT 权限。
>
> 特别强调两点。第一，我**没用关键字黑名单**——黑名单永远列不全。我实测过 `TRUNCATE`、`INTO OUTFILE`、`SELECT SLEEP(600)` 这三类都能绕过朴素黑名单。所以主防线是**白名单**：不是"禁止什么"，而是"只允许什么"。
>
> 第二，语法解析用 **fail-closed**：解析不了就拒绝。实测真起了作用——MySQL 的 `INTO OUTFILE` 语法 JSqlParser 解析不了，这条写文件攻击在进关键字扫描之前就被拦下了。
>
> 最后，真正的兜底不是代码，是**只读账号**。我用这个账号实测执行 DELETE 和 DROP，都被 MySQL 直接拒绝。代码可能有漏洞，但物理权限没有。

### Q3 ★★★ Agent 和普通的大模型函数调用有什么区别？

> Agent 不是"更聪明的模型"，而是"**模型 + 工具 + 一个循环**"。普通函数调用流程写死：先调 A 再调 B；Agent 把决定权交给模型——它自己判断要不要调工具、调哪个、传什么参数、调几次。
>
> 实测问"上个月支出多少"，模型先调 `getDatabaseSchema` 看表结构，再生成 SQL 查总额，**接着自己又调了一次去拿 `CURDATE()`**，确认"上个月"是整月——这三步顺序没有任何一行代码规定它。
>
> 主循环设了 6 轮上限：模型可能陷入反复调工具的死循环，每轮都是付费请求，所以上限既是稳定性也是成本保护。

### Q4 ★★★ 你怎么评估你的 Agent / RAG 效果？

> 我做了 **26 条评测集、7 个难度级**，从单表聚合一直到多跳关联和安全边界。
>
> 判分方式我特意**没选"让大模型当裁判"**，而是**预先写好黄金 SQL、比对数字对不对**。两个原因：一是比对结果比比对写法可靠——同一个问题有很多条正确 SQL，比 SQL 文本会把"写法不同但答案相同"误判为错；二是 LLM 当裁判会引入第二个不确定性。
>
> 但更有意思的是过程。第一轮 20 条全过 100%，**我没当成好消息**——一个 100% 通过的评测集，区分度是 0，改个参数还是 100%，我就判断不了改动好坏。所以又加了 6 条更难的，还是全过；这才说明**是这个 schema 本身太简单**，不是评测集偏易。
>
> 中间还出过一次"失败"：有条题模型答"2025 年没有任何支出记录"被判错。看原文才发现**回答是对的，是我的判分器只认数字 0**。更讽刺的是我第一版修法又造出新 bug——把 `"0"` 当字符串匹配，"12000"因为含 0 也被判对。
>
> 这件事让我意识到：**评测器本身也需要被评测**。

### Q5 ★★ 你已经能跑了，为什么还要重构成图？

> 因为手写版的问题不是跑不了，而是流程**藏在 for/if 里——看不见、测不了、插不进钩子**。想验证"SQL 被拒后会不会重试"，得把整个循环跑起来；想插个人工确认点，得改循环内部代码。图把流程变成了**数据**：节点和边可枚举，于是能画出来、能逐节点单测、能在任意节点挂拦截器。
>
> 但有个**意外收益**是我跑对比才发现的：同一个问题，手写版 **4391 token**，图版 **1098 token，降了 75%**。原因是 tool-calling 接口是无状态的，每一轮都要把系统提示词加工具定义加全部历史整段重发；而图里每个节点只发自己需要的那一小段。我原本以为重构只是换可观测性、不会省成本。
>
> **代价也要说**：图版回答更简短，因为 `report` 节点只看得到结果集、看不到中间过程。可以把 report 提示词写详细些补回来。

### Q6 ★★ Agent 写错了 SQL 怎么办？

> 让错误「**可行动**」。模型自愈的前提不是它更聪明，而是它看到的信息够不够改。
>
> 工具执行失败**不抛异常，而是把错误当成正常返回值**回传——抛异常会直接中断这轮对话，模型永远不知道发生了什么。
>
> 但只回传原始报错不够，我做了一层**错误整形**：把 MySQL 错误码翻译成 `errorType` + `hint`，并且**按类型分类**。这是实测跑出来的——最初所有拒绝都返回同一句"不要绕过"，结果模型把"表名拼错"也当成安全红线直接放弃了，而拼写错误恰恰是它**应该**改的。
>
> 还有个坑：`SchemaTool` 把 `user` 表展示给模型、`SqlGuard` 又不允许访问，模型"看得见摸不着"。我改成两者**共用同一份白名单**——单一事实来源，问题从结构上消除，不是靠护栏兜住。

### Q7 ★★ 为什么不用向量检索？现在不都是 embedding 吗？

> 我**实测过**——DeepSeek 不提供 embedding 接口，`POST /embeddings` 直接返回 **404**。其他厂的 Key 我也没配。
>
> 但更关键的是：在这个场景下**不需要**。表结构的召回信号很明确——表名、字段名、注释、**字段真实取值**，这些是关键词能精确匹配的；而语义相似度反而可能把不相关的表拉进来。
>
> 而且我把打分函数抽象出来了，`SchemaRetriever.score()` 就是**预留给向量版的替换点**——换成余弦相似度只需要改这一个方法，召回逻辑完全不用动。

### Q8 ★ 这个项目最难的地方是什么？

> 不是写代码，是**排查"看起来对但结果是错的"**。这类 bug 最坑。
>
> 举个例：我用 curl 测 Web 接口，一连几轮都在"修 Agent"——改提示词、加规则、调时序，每次都变一点点，但都不对。最后我把**服务端实际收到的问题原文**打出来，一行就定位了：中文变成了 13 个乱码字符。
>
> 根因是 Git Bash 里的 `curl.exe` 是 Windows 程序，中文参数经 ANSI 代码页二次编码。**症状特别骗人**：接口 200、SQL 语法正确、模型也能答，只是答案永远是错的。而浏览器发的是标准 UTF-8，所以真实界面根本不受影响。
>
> 这件事让我总结出一条：**当输入不可信时，先打印输入，再怀疑逻辑。**

### Q9 ★ 如果表有几百张，你这套还成立吗？

> 已经做了那个实验。我把表放大到 **40 张**跑召回：命中 8/8，**压缩率 87.4%**（3412 → 431 token）。
>
> 但我也**诚实说局限**：通用主键名会误扩——实验里"员工工资由哪些项组成"误扩进了 `erp_purchase_detail`，因为它们的 `detail_id` 撞名了。
>
> 到几百张表时我会做三件事：① 召回引入 **IDF 项**（几十张表时区分度不大，几百张时才有意义）；② 关联扩展**结合字段注释语义**再判一次，而不是纯名字匹配；③ 考虑上向量召回补关键词的盲区。

### Q11 ★ 为什么用 Spring AI Alibaba，不用 LangChain4j / 直接用 Python 的 LangGraph？

> 我是 **Java 技术栈**，目标是 AI 应用开发，而 Python 生态在落地时往往和公司的 Java 后端是两套。Spring AI Alibaba 是 Spring 官方体系里的，和我的 Spring Cloud 背景能接上，这是最实际的理由。
>
> 另外我**同时留了手写版**——因为我不想让框架掩盖我到底懂不懂。手写那版证明了循环、工具分发、错误回传这些我都能自己做；图版证明我能在工程上把它规范化。两个都有，说话才有底气。

### Q12 ★ 这个项目和你参考的 dataagent 有什么不同？

> 我参考了它，也参考了 WrenAI 的语义层和 Vanna 的 Schema RAG，但**没有照抄**。
>
> 三个主要差异：① 我的数据是我**自己系统的真实业务数据**（中文注释、中文枚举值），不是公开数据集，所以踩的坑是真坑；② 我做了 **26 条评测集**，把效果量化了，不是跑通就算完；③ 我**两套实现并存**并做了同题对比，拿到了 token 降 75% 这个数字——这是我自己实测的，不是文档上抄的。

### Q13 ★★★ 支持多轮对话吗？用户追问「那收入呢」怎么办？

> 支持。加了一个 `rewrite` 节点做**指代消解** —— 用户说「那收入呢」，
> 它把历史里的话题补进去，改成「上个月收入是多少」再往下走。
>
> 我特意**没有**把历史直接塞进 generate 的提示词：generate 已经在同时处理
> 时间、收支方向、分类、选表这四件事，实测总会漏一项；再塞进"理解指代"只会更糟。
> 拆成独立节点之后职责单一，而且改写结果会在界面上单独显示一行 ——
> **指代消解一旦错了，那一行是最早暴露的地方**，比等 SQL 和答案出来再怀疑快得多。
>
> 有个成本细节值得说：**没有对话历史时这个节点完全不调用模型**。
> 所以 26 条单轮评测用例的行为，和加这个功能之前**一模一样** ——
> 这也是我敢在最后一天动核心链路的前提：影响面是明确的、可验证的。
>
> 历史本身不放在图里。图每次都是新建的（第 9 步那个状态残留坑要求如此），它天然无状态，
> 所以"记住上一轮"由调用方负责：命令行版是一个局部变量，Web 版是
> `sessionId → 历史` 的 Map。隔离和记忆这样彻底解耦，不会出现"想清空上下文却清不掉"。
>
> 诚实说一句：我**还没有为多轮单独做评测集**，所以「改写准确率」目前只有手工样例
> （三轮追问全部正确），没有量化数字。要补的话得给评测用例加"前序轮次"字段。

### Q14 ★★★ 你的业务口径（收入/支出/净额）是怎么定义的？

> 一开始我把口径写在 `generate` 的提示词里，用自然语言描述。它能跑，但有三个问题：
> ① 用户说法和口径不是一一对应——问「我赚了多少」，提示词里没这个例子，只能靠模型猜；
> ② 改口径要动 Java 代码重新编译；③ 没有单一事实来源，问"结余怎么算的"，
> 答案散在几百字提示词里。
>
> 后来我把它抽成 `config/metrics.json`：指标名、别名词表、聚合表达式、适用条件全是配置。
> 匹配是**纯规则**（问题里出现别名即命中），零 token —— 这和第 10 步 `verify` 节点同一个判断：
> **能用规则算清楚的事，不该交给概率模型。**
>
> 有两个设计点值得说：
> 一是**口径冲突**。「收入减掉支出还剩多少」里同时出现了「收入」「支出」「还剩多少」，
> 会命中三个指标，但这句话只有一个口径。我让「净结余」在配置里声明
> `supersedes: ["收入","支出"]`，命中它时把这两个吸收掉 —— 仍然是规则，不是让模型猜。
> 二是**适用范围**。指标给的是"求总额"的口径，但「属于『支出』类型的分类有几个」
> 虽然字面有「支出」，问的却是个数。所以我加了 `skipWhen` 词表，这类问题不注入指标。
> 这两个词表命中的例子**都真实存在于我的评测集**（E05 / E06），不是预防性设计。

**追问：那语义层带来了多少提升？**

> **在这套评测集上，是 0。** 我跑了 A/B：开和关都是 24/24，平均 token 1656 → 1652。
>
> 原因是我这套题对当前模型太简单 —— 这点我在第 8 步就确认过（26 条全过、区分度为 0）。
> 语义层给出的表达式，在最难的几条上也和模型自己推导的一致，所以端到端测不出差异。
>
> **但我不认为它白做**。一是它把口径变成可维护、可测试的东西（`Step13Main` 能零成本验证匹配，
> 改配置不用重新编译）；二是**它立刻逼出了一个真实的 Bug** —— 注入的正确表达式
> `SUM(CASE WHEN status='收入' THEN amount ELSE -amount END)` 用减法表达方向，
> 字面上没有「支出」二字，结果被我自己的字面规则误判成"漏了支出条件"，
> 一条完全正确的 SQL 被拦到失败。
>
> 要真正量化语义层的收益，需要的是**更难、更细的评测集**：同一口径的 10 种说法、
> 改口径后的一致性。这正是我下一步要做的事 —— 「测不出来」本身也是个结论，
> 它告诉我评测集的区分度不够。

**追问：那为什么不用向量检索做这一步？**

> 因为这一步判断的是"问题里有没有出现这个词组"，是确定性的字符串操作。
> 真正需要语义理解的是"用户说的『赚了多少』到底指收入还是净结余"——
> 这个我用**别名词表**显式列出来（可查、可改、可单测），而不是让模型每次现场猜。
> 猜的结果不可复现，配置的结果可以。
> 向量召回更适合的是**表结构召回**（第 7 步），那里匹配的是"语义相近"而非"词面相同"。

## 五、8 条工程教训（"你怎么排查问题"的素材库）

| # | 教训 | 一句话证据 |
|:-:|---|---|
| 1 | **先测量，再下结论** | 看到"Windows + 乱码"就断定 GBK，改完发现是合法 UTF-8，白折腾一轮 |
| 2 | **改配置前，先想它会不会影响另一个方向** | `chcp 65001` 修好了输出，却把输入搞坏了 |
| 3 | **密钥绝不进命令** | `echo "${KEY:-未设置}"` 在变量已设置时打印的是**值本身** |
| 4 | **修一处编码，要检查所有同类路径** | 项目有 3 条独立输出路径，只改一条不够 |
| 5 | **评测器本身也需要被评测** | 误判过一次，第一版修法又造出新 bug；100% 通过 = 区分度 0 |
| 6 | **「框架能跑通」和「框架用对」是两回事** | 写隔离性测试才发现 `CompiledGraph` 状态跨 invoke 残留 |
| 7 | **「程序变笨了」之前，先确认它收到的是什么** | 打印输入一行定位：中文在传输途中就坏了 |
| 8 | **依赖「字面」的规则，会在换种写法时失效** | 同一个坑踩三次：`create_time` 的位置、「8 月」的写法、`-amount` 的表达 |

> **用法**：面试官问"你遇到过什么难题 / 怎么排查"时，**挑 1 条讲透**，不要全铺开。
> 最推荐 **第 8 条**（三次踩坑后提炼出的规律，最能体现复盘深度）、
> **第 6 条**（有技术含量）或 **第 7 条**（有反转、有方法沉淀）。
>
> **第 8 条怎么讲**：三次都是"把一条正确的 SQL 判成错的，然后进入注定失败的重试循环"。
> 根因是我用「某个词有没有出现」近似「某个语义有没有被表达」——
> 写法固定时碰巧都对，一旦给表达方式增加自由度就立刻失效，
> 而它的失效在手工抽样时**几乎看不出来**（我抽的那几条恰好都正常）。
> 做法是每次给 SQL 增加表达自由度就回头过一遍字面规则，并且让规则有可观的诊断输出。

## 六、主动坦白的局限（比被问出来好）

先自己说，显得诚实且清楚边界：

1. **评测集已饱和**：26 条全过，说明它对改动不敏感，**不能用来验证参数调整**。语义层的 A/B 就是活证据——开和关都是 24/24、token 1656 → 1652，收益在端到端上根本测不出来。要恢复区分度需要加压：放大 schema 到几十张表、同一口径的多种说法、歧义问题（"最近"指多久）。
2. **召回参数是拍的**：`MAX_RELATED` / `DEFAULT_TOP_K` 没有数据支撑，因为当前库只有 4 张表，调了也看不出差别。
3. **单轮结果有随机性**：模型输出不完全确定，判断改动是否有效**必须多跑几轮看趋势**。真实项目应该把评测接进 CI。
4. **Web 层是最小演示版**：无鉴权、无限流、无访问日志、无优雅关闭。定位是"给人看效果"，**不是"给人用"**。要上线至少还需要登录态、按用户隔离数据、请求限流、服务端密钥管理。
5. **数据是单用户的**：`t_account` / `t_transaction` 没有 `user_id`，这是复用原系统带来的，没为了好看去改它。
6. **语义层的别名词表靠人工维护**：模型能自己理解"赚了多少"指什么，但配置化的词表不能——代价是"覆盖不全会漏"，收益是"覆盖到的部分行为确定、可单测"。目前只覆盖金额类（收入/支出/净结余/笔数），账户余额、预算类还没进配置。
7. **多轮对话没有量化评测**：改写准确率目前只有手工样例（三轮追问全对），要补得给评测用例加"前序轮次"字段。

> 主动说局限的**收益**：面试官会觉得你"知道自己在做什么、知道边界在哪"，而不是"做完就以为完事了"。
